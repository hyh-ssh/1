# LiteLLM endpoint compatibility: bounded gateway scope

Reference for endpoint-level comparison: LiteLLM repository snapshot [`f0e671f7549665b39a562149d5e654682b9e6a51`](https://github.com/BerriAI/litellm/tree/f0e671f7549665b39a562149d5e654682b9e6a51). This is a **pinned design reference**, not a claim of LiteLLM feature parity or a runtime dependency. The matrix below describes *this gateway's* HTTP contract; an endpoint existing here does not imply that every upstream implements it or that every request/response field is portable. Gateway API-key authentication, alias routing, policy and upstream transport checks still apply.

| LiteLLM comparison axis (pinned snapshot; interface only) | Gateway public endpoint | Gateway behavior | Limits / route requirements |
| --- | --- | --- | --- |
| Model discovery | `GET /v1/models` | List accessible model aliases. | Filtered by the caller's API-key model allowlist, not the full upstream model catalog. |
| Chat completions | `POST /v1/chat/completions` | Chat JSON and SSE; retain supported tool, visible reasoning and reported usage fields through normalization. | Same-protocol fields are rebuilt, not byte-for-byte proxied. Cross-protocol mappings are bounded by what the selected adapter can express. |
| Anthropic messages | `POST /v1/messages` | Anthropic-shaped request; native Anthropic route or explicit gateway translation where supported. | Requires `messages` and positive `max_tokens`; translation is not an arbitrary Anthropic feature pass-through. |
| Embeddings | `POST /v1/embeddings` | Non-streaming embedding request via supported provider route. | `input` required; `stream: true` rejected. Unsupported routes return 501; no implicit provider conversion. |
| Image generation | `POST /v1/images/generations` | Preserve the native JSON request/response and public model alias. When a streaming request receives an actual upstream SSE stream, forward partial-image, completed and error events frame by frame with a flush after each frame. | `prompt` required; a provider returning non-SSE for a streaming request is rejected rather than inventing partial-image progress. Endpoint presence does not guarantee image or streaming support on a given route. |
| Responses | `POST /v1/responses` | Independent OpenAI Responses API JSON/SSE. Keep raw input/unknown JSON keys for a **rebuilt** upstream request; expose public model alias in JSON and raw `response.*` events, including tool-argument fragments and completion usage. | Only routes with provider `supports_responses=true` participate. Otherwise 501 `responses_unsupported` before any upstream attempt; **never** fall back to Chat. SSE failures before the first frame return JSON error; after start emit one error frame, no success terminator. Completed/incomplete event carries usage once, and each emitted frame is flushed. |

## DeepSeek profile and reasoning gate

DeepSeek-specific **Chat** request rules require an explicitly configured `openai_compatible` provider with `compatibility_profile: "deepseek"`; a model name or alias containing “deepseek” is insufficient. The provider's selected, **active** model record must also declare `capabilities.reasoning=true` before the multi-turn reasoning-content compatibility workaround is allowed. When thinking is enabled, an assistant message missing reasoning content may receive a single space for upstream compatibility; this is not generated reasoning or a promise of chain-of-thought disclosure. The DeepSeek profile maps supported thinking settings, replaces OpenAI `reasoning_effort` with the supported `thinking.type` shape, and does not forward an unsupported `thinking.budget_tokens` field. It filters unsupported tool definitions. It does **not** opt the provider into `/v1/responses`: `supports_responses` remains independent and explicit.

After applying migration `0008_provider_compatibility_profile.sql`, choose **DeepSeek** for the OpenAI-compatible provider in the administrator Operations pane (or set the provider's `compatibility_profile` to `deepseek` through the admin API). Leave other providers at the default `generic`. For each relevant *provider model*, explicitly enable its `capabilities.reasoning` setting if that upstream model supports reasoning; this setting is separate from the public alias and from `supports_responses`. A request must still select that route and explicitly enable thinking to activate the workaround.

For the single-space workaround, **return the actual `reasoning_content` from each assistant turn** in the next multi-turn request whenever the provider supplies it. A synthetic space loses the real reasoning chain and may reduce continuation quality; it is only inserted when this request explicitly enables thinking and the selected upstream model explicitly advertises reasoning capability. An absent/inactive model capability record does not qualify. This rule does not apply to Messages or Responses.

Chat SSE forwards sparse tool-call indexes, IDs, names and argument fragments without filling missing delta fields; reasoning is a separate `reasoning_content` delta, not text wrapped in `<think>`. It does not represent client-side tool execution or token-by-token progress. Native Messages retains Anthropic events and request fields; conversions to OpenAI-compatible/Gemini only accept representable text/function tools and reject unsupported signatures/extensions before upstream dispatch.

OpenAI-compatible Chat providers may name returned reasoning `message.reasoning` or `delta.reasoning` instead of `reasoning_content`. The gateway normalizes a valid returned reasoning string to `reasoning_content` in JSON and SSE when the canonical field is absent, matching the pinned LiteLLM OpenAI response path; it does not synthesize a chain from `usage.reasoning_tokens`. This **response** normalization is independent of the provider's DeepSeek request profile. A provider can still ignore `thinking.type`, report reasoning tokens while thinking is disabled, or omit reasoning text altogether. Compare the raw upstream fields, normalized output, finish event and usage before attributing a missing chain or ineffective thinking control to the gateway.

### Diagnosing a cut-off Chat stream

Inspect the **raw** upstream and gateway SSE (including the last `choices[].finish_reason`, usage and `[DONE]`) for the same request ID/time and selected provider route. A `finish_reason: "length"` followed by `[DONE]` is a completed response that hit an output-token limit: review the caller's `max_tokens` or `max_completion_tokens`, the upstream model's own limit and any reasoning-token budget. Increasing a limit is only useful when the selected model/provider permits it. A missing terminal event is a failed/incomplete stream, not a successful generation; check the provider's `timeout_ms` (default 30000 ms, applies to the whole upstream request), reverse-proxy timeout and upstream transport logs. This gateway returns a JSON error before output or an SSE error frame after output, without inventing `[DONE]`. If the gateway received and flushed the full stream but a client shows less, inspect that client's SSE/error handling and any intervening proxy. Text such as `<｜DSML｜ invoke name="Bash">` inside `delta.content` is model output, **not** a `delta.tool_calls` invocation; only a structured tool-call delta should be treated as a tool call. Neither the text fragment nor mock tests alone identify which of these paths occurred in production.

## Explicit exclusions

- No LiteLLM runtime, automatic provider capability discovery, broad endpoint-parity certification, automatic Responses→Chat fallback, or inferred reasoning capability by model name.
- No assertion that untested LiteLLM snapshot behavior applies to all providers; no blanket compatibility claims for additional endpoints (audio, batches, files, etc.), multimodal/tool shapes, provider-specific SSE variants or billing details not covered by gateway tests.
- Do not forward raw client credentials, hop-by-hop headers or unvalidated HTTP bodies to gain apparent parity. Requests are decoded and rebuilt; normalized accounting and public aliases remain gateway responsibilities.
- No automatic SSE keepalive comments or new `/v1/...` path aliases in this change. Before the first business frame, an upstream failure is still eligible for a JSON HTTP error and existing safe route fallback; after output, the route cannot change, and a stream error must not be followed by a success terminator.
- Mock upstream tests with delayed, explicitly flushed frames prove this process's HTTP flushing contract only. They do not establish live reverse-proxy buffering, client rendering behavior, or a particular deployed LiteLLM configuration.

Responses HTTP mock coverage: `backend/internal/httpapi/responses_test.go` (request reconstruction, function-call SSE fragments, event names, alias and usage, single completion, pre/post-start errors and per-frame flush). Run `cd backend && go test ./internal/httpapi -run 'Test(Responses|GatewayResponses)' -count=1` to exercise the targeted tests; this is not a live-provider interoperability certification.
